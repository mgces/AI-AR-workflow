# Performance impact — coredump UID whitelist (AR 20260723)

## What changed on the hot path
`CoredumpRequestValidator::CheckCoredumpUID(uid)` previously did a linear search over
a hardcoded `std::vector<int>{0,1202,7005}`. It now calls
`CoredumpUidWhitelist::GetInstance().IsAllowed(uid)`, which does the **same** linear
search (`std::find`) over a cached vector — the only added work is one mutex
`lock_guard` (uncontended: coredump requests are rare, one per process crash).

## Cost model
- **Steady state per request:** `std::find` over N≈3–7 ints + one uncontended mutex
  lock/unlock. O(N), N<10 → sub-microsecond, and it runs **once per coredump
  request** (a crash event, not a per-frame/per-IPC path).
- **One-time load:** on the first request, `LoadLocked()` reads
  `/system/etc/fault_coredump.json` once and `cJSON_Parse`s it, then caches
  (`loaded_` flag). No file I/O on any subsequent request. This is a config file
  already shipped with the binary, read by other faultloggerd code paths already.

## Net impact
Negligible. The per-request cost is unchanged in order (a small vector scan) plus a
single uncontended lock; the one-time parse is paid once in the process lifetime and
is strictly less work than the existing `faultloggerd` startup. No regression path
exists for a coredump-gated feature.

## Verification
Functional correctness (allow/deny for in/out-of-list UIDs) verified on device in P4
(`UID 0 is in uidList` / `UID 9999 is not in uidList`, rc=0/REQUEST_REJECT). No
timing-sensitive surface to benchmark at this scale.

# Power impact — coredump UID whitelist (AR 20260723)

## Change summary
The whitelist is a passive, lazily-loaded lookup consulted only when a coredump is
requested. It introduces **no new threads, timers, periodic work, wakeups, or I/O
loops**.

## Analysis
- **No new active components:** the `CoredumpUidWhitelist` singleton is a pure
  in-memory cache (`std::vector<int>` + a mutex). It does not register with hiview,
  does not open sockets, does not poll.
- **Triggered, not scheduled:** `IsAllowed()` runs only on the coredump request path
  (`CoredumpRequestValidator::IsAuthorizedUid`), which fires on a process crash —
  already an exceptional, non-periodic event handled by the running `faultloggerd`.
- **One-time file read:** `/system/etc/fault_coredump.json` is read exactly once (on
  first request) and cached (`loaded_`). No repeated disk reads that could keep a
  device or CPU out of idle.

## Net impact
None. The change adds no background or periodic activity, so it cannot affect idle
power, suspend, or wakeup behavior. There is no power surface introduced to measure.

# Stability impact — coredump UID whitelist (AR 20260723)

## Change summary
Replaces a hardcoded UID set with a config-driven, lazily-loaded, cached, mutex-
protected whitelist. Fail-safe by design: any config error returns the prior default
set `{0,1202,7005}`, so a bad config can never block all coredumps or open the gate.

## Safety properties
- **Fail-safe, fail-closed-to-defaults:** file missing / unreadable / malformed JSON
  / missing array / empty array all fall back to `DefaultUids()` and log
  (`DFXLOGE`). Verified by `FailsSafeOnBadConfig_001` and `AllowsDefaultUids_001`.
- **Thread safety:** `IsAllowed()` and `LoadForTest()` take `std::lock_guard` on a
  `mutable std::mutex`; the cached `uids_`/`loaded_` are only mutated under the lock.
  `GetInstance()` uses a function-local `static` (thread-safe init).
- **No resource growth:** no per-request allocation (vector cached), no new file
  descriptors, no new threads, no new signal handlers. `faultloggerd` was already a
  long-running daemon; this adds a static singleton to it.
- **No loop/recursion risk:** the load path is straight-line (read → parse → fill or
  fallback); `IsAllowed` is a single `std::find`.
- **Signature preserved:** `CheckCoredumpUID(uint32_t)→bool` semantics unchanged; the
  caller `IsAuthorizedUid` is unmodified, so no caller-side stability regression.

## Device verification
P4 ran the live `faultloggerd` (new binary + matching `libdfx_util.z.so`) on rk3568:
the daemon started cleanly, served coredump requests, and returned allow/deny per the
whitelist without faulting. `evidence/phase4/` holds the hilog + sha256 proof.

## Net impact
No stability regression. The change is localized, mutex-protected, fail-safe, and
adds no threads/timers/resources. The only operational note is deployment: the new
binary needs its matching `libdfx_util.z.so` on the target image (handled in the P4
deploy script and noted for P6 release notes).
