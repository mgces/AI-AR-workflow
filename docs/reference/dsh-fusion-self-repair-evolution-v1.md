# DSH 融合、自修复与自迭代方案 v1

日期：2026-09-07。本文保留 v1 设计基线；现已开始分阶段改造，实际完成范围和验证结果见[实施状态与未完成项](/reference/dsh-fusion-implementation-status)。本页的拟议接口不代表已全部实现。

选型已确定：**以 GitCode `runtime/dsh-ohos` 为唯一运行主干，吸收本地模块选择与修复策略，建立任务内自修复和跨任务自迭代两个闭环。** 本方案基于上轮已审阅的 GitCode `415c57b`，本地素材来自 `dsh-workflow/`。基础差异和验证结果见[两套实现对比](/reference/dsh-implementation-comparison)。

## 1. 目标与首期交付

用户启动需求或 AR 后，系统能按阶段准备上下文、派发任务、识别失败、在已授权范围内修复并重新验证；运行中断后能接续。成功与失败的真实记录用于改进后续模块选择、诊断顺序和修复策略。

| 能力 | 本方案定义 | 首期交付 |
|---|---|---|
| 融合 | 一套任务协议、一套调度状态、统一模块与策略入口 | 保留远端 R1–R9、P0–P8、SQLite、租约、幂等、父子工具分面；迁入本地策略资产 |
| 自修复 | 解决当前 run 的失败，并重新取得该阶段及受影响下游的有效证据 | 优先打通 P4 构建失败；覆盖环境重试、日志诊断、候选补丁、P2 回退重走、预算与停止条件 |
| 自迭代 | 从多个 run 的已核验结果提出策略改动，评测后形成可回滚版本 | 经验采集、候选生成、回放／执行评测、影子运行、有限灰度与版本回滚 |
| 持续运行 | 模型任务由宿主执行，确定性长作业由受管执行器运行 | 宿主断开后保存状态；执行器存活时继续已有构建；需要推理时等待宿主恢复 |

首期以**一个源码工作区、一个构建环境、同一时刻一个写入任务**验收。架构保留跨宿主能力，首期不以并发改码或全自动真机／发布作为完成条件。

自动化采用分层范围：常规重试、范围内补丁与再验证按 run 的策略连续执行；需求决策、设计边界变化和既有 P1／P6／P7／P8 确认仍沿用原流程。模型负责诊断与产出候选，确定性代码负责调度、预算、核验和推进。

## 2. 已有能力与本次新增

| 资产 | 处理方式 | 尚需补齐 |
|---|---|---|
| 远端 `core/TaskController`、SQLite、host binding、工具 catalog | 直接作为基础，兼容已有工具名和核心参数 | 长作业、资源生命周期、修复 episode、持久预算、策略版本绑定 |
| 远端 `RequirementWorkflow` | 保留正式需求状态与产物校验 | 接入模块路由和结构化返修指导；语义事实缺失仍交用户补充 |
| 远端 `DeliveryWorkflow`、Python adapter／bridge | 保留 Python 证据验证、consent 和 sync | gate 异步受管执行、失败归一、repair/reset 调用与对账 |
| 本地 29 个模块及依赖配置 | 逐项迁入版本化 registry | 环检测、缺失能力诊断、确定性排序、模块 hash、必需／可选区分 |
| 本地 failure normalizer、repair strategies | 作为策略素材 | 结构化失败优先、适用范围验证、停止条件、实际执行约束 |
| 本地 experience proposals | 保留聚合和候选的思路 | 改用已核验事件，关联修复前后与真实使用记录，补评测和发布流程 |
| 本地需求投影和独立控制器 | 归档为实验参考 | 正式运行不并入第二套需求／开发状态机 |
| 原有 Python `gate_build.py`、`gatelib.py`、`advance.py` | 继续作为开发阶段权威 | 增加兼容的执行关联、只读检查与互斥边界；不改业务放行标准 |

**已有 Python 能力需要准确复用：**

- `gate_build.py` 会实际启动构建、收集新鲜日志、检查声明产物和静态检查结果，并输出 repair packet；其中已有重试／修复轮次及升级建议。
- `gatelib.repair_round_metadata()` 的计数和导航建议目前是辅助控制信息；它与跨 task、跨进程的强制预算不是同一层能力。
- `advance.py repair --reason ...` 可在有效的签名 v3 契约和 P1 consent 下回到 P2，保留有效设计基线；行为、公开 API、依赖或验收变更需要 `reset` 回 P1。
- `repairs/current.json` 以及 `P4_P5` 等历史 scope 字段是导航信息，部分名称使用旧逻辑编号。适配器必须版本化解释，不能按字符串直接拼出当前物理阶段或减免验证。

新增控制器预算与 Python 升级建议取更严格的约束；保留原始字段，不覆写已有 packet 或签名证据以“统一”统计。

## 3. 总体架构与状态归属

```text
宿主父 agent／领域 worker
    │ 既有 MCP 任务协议 + 新增受管执行接口
    ▼
runtime/dsh-ohos
    ├─ core：任务、事务、幂等、预算、资源、事件
    ├─ workflows
    │    ├─ requirement：需求产物、决策、追溯、回退
    │    └─ ar-delivery：阶段调度、repair/reset、Python 对账
    ├─ policy：模块解析、失败分类、修复计划、策略版本
    ├─ execution：作业提交、进程树、日志、取消、恢复
    └─ evolution：经验、候选、评测、灰度、回滚
         │                          ▲
         ▼                          │ 只消费核验结果
  Python gate／advance ──── 已核验的证据与完成记录
```

| 状态 | 唯一依据 | 写入方 |
|---|---|---|
| 开发阶段、签名证据、功能指纹、业务 consent | 现有 Python pipeline 与 manifest | 现有 Python 权威入口 |
| 需求阶段、产物快照与需求决策 | 远端 RequirementWorkflow 校验结果与 SQLite 记录 | RequirementWorkflow |
| 任务、attempt、资源、作业、修复预算 | 同一控制器数据库 | TaskController／受管执行器 |
| 策略版本、评测及灰度状态 | 不可变策略包 + 数据库发布记录 | 策略发布服务 |
| 推荐、实际使用、执行结果、最终业务结果 | 分开保存的事件与证据引用 | 各环节记录，父级核验后接纳 |

DSH plugin 和 MCP 是同一业务内核的入口；先复用远端 catalog。标准 MCP SDK 替换属于独立基础设施改造，后置进行，避免与自修复同时扩大变更面。

## 4. 模块选择与上下文准备

每个任务的上下文由五部分组成：阶段目标、有效输入、必须遵守的契约、必要 Skill、当前失败证据。通过原有 `ohos_task_context` 返回，不增加一套模型主管。

解析顺序：

1. 读取 run 固定的 `policy_version`、原始输入和有效需求／AR 契约，确定必需能力。
2. 加入阶段必需模块，再按领域标签、能力和失败类别选可选模块。
3. 展开依赖并验证：不存在的模块、循环依赖、未覆盖的必需能力必须可诊断；必需模块不满足时阻塞该任务。
4. 对候选排序，按可配置上下文预算截取可选内容；必需内容超过预算时拆任务或明确报告，不能静默丢弃。
5. 返回 `module_id/version/hash/reasons/required/selected_sections`。宿主记录实际读取／使用情况，缺乏观测时标为 `unknown`。

首期只支持登记过的模块和文件路径。`contextCost` 作为估计，不冒充准确 token 数。每次读取的内容必须与 run 绑定的模块 hash 一致；发生变化时要求重新生成上下文或显式切换策略，防止中途悄然换规则。

## 5. 任务内自修复闭环

### 5.1 运行过程

```text
作业结束或任务校验失败
  → 核验执行身份、日志、manifest 与当前基线
  → 建立／续接 repair episode
  → 分类失败、检查范围和剩余预算
  → 生成修复计划
       ├─ transient：状态核实后重试
       ├─ local repair：候选补丁 → 范围检查 → 核验后导入
       ├─ implementation repair：Python repair → P2→P3→P4 重走
       ├─ design reset：形成变更原因 → P1 设计及既有确认
       └─ blocked：说明缺失输入、授权、环境或预算
  → 运行原 gate／受影响的下游门禁
  → 核验新的证据
       ├─ 满足修复要求：resolved，继续原 workflow
       ├─ 仍失败且有预算：带新证据继续本 episode
       └─ 状态未知／重复无进展／预算耗尽：停止自动执行
```

`episode` 是同一故障及其衍生修复的持久记录，附着于原 run。诊断、补丁和复核作为原任务下的子工作项，通过已有领取／提交协议调度；不会额外制造一条 P0–P8。

### 5.2 动作等级

| 动作 | 可自动执行的条件 | 停止／回退条件 |
|---|---|---|
| 日志读取、分类、补充诊断 | 当前证据可核验，操作只读 | 证据无法绑定当前 run 或日志来自未知执行 |
| 相同命令重试 | 有瞬态故障依据、上次作业已确定停止、未超预算 | 同输入与同错误无变化；不能把未知执行结果当失败重跑 |
| 环境调整 | 仅使用环境 profile 已允许的目标、工具链选择和作业内参数 | 需安装未知依赖、改凭据、修改共享配置或改变签名目标 |
| 补丁修复 | 已授权实现范围内，补丁基线匹配，经必要的独立检查 | 行为／API／依赖／验收变化，或范围无法确定 |
| 回 P2 重走 | Python 接受 `repair`，设计契约仍有效；先回退再修改冻结源码 | 非 v3 契约、无有效 P1 consent 或存在设计变化时改走 P1 |
| 需求文档返修 | 补齐格式、追溯等已知内容，事实来自有效输入 | 不得替用户补造事实、架构选择、评审结论或 GA 批准 |

首期的 `same_phase` 自动修复仅允许无需改源码／测试内容的执行恢复。涉及源码、测试或构建定义的修改，优先走现有 P2 重走路径；以后如需更窄回退，必须增加明确的权威接口及回归验证。

### 5.3 修复计划契约

新增 `repair_plan` 至少包含以下字段，全部属于项目拟议接口：

| 字段组 | 内容 |
|---|---|
| 身份 | `run_id/task_id/attempt_id/episode_id/operation_id/expected_revision` |
| 基线 | `policy_version/contract_hash/source_digest/input_digest/evidence_epoch` |
| 诊断 | `failure_class/failure_fingerprint/classifier_version/root_cause_hypothesis/evidence_refs` |
| 动作 | `action/target_phase/allowed_paths/forbidden_changes/required_modules` |
| 再验证 | `must_rerun/invalidated_evidence/required_downstream`，由权威动作确定 |
| 控制 | `budget_reservation/stop_conditions/approval_required/plan_digest` |

模型可提出根因和候选方案，最终动作由控制器根据基线、范围和政策确定。结构化 Python verdict 与证据优先，其次使用当前执行日志；日志正则和模型推断不能覆盖签名异常、过期证据或 Python 拒绝。

### 5.4 强制预算与无进展检测

下列数值为 v1 试点默认值，待基准运行后调整；不是现有实现或效果承诺。

| 预算 | 建议初值 | 计数规则 |
|---|---|---|
| 同故障、同输入的额外重试 | 最多 2 次 | 首次执行不计重试；每次实际启动前预占 |
| 同 episode 的候选补丁 | 最多 2 个 | 包含被范围检查或测试拒绝的候选；更换模型不重置 |
| 一个 run 的自动修复 episode | 最多 3 个 | 同一需求的 repair/reset 保留累计消耗 |
| 重复无进展 | 连续 2 次相同主错误与相同补丁／输入即停止 | 多做日志分析不视为修复进展；错误条数减少只是信号，不是成功 |
| 构建单作业时间、累计机器时间、模型任务额度 | 每个环境 profile 配置 | 使用测得的构建基准；缺少模型 token 计量时限制调度次数，不虚构 token 上限已生效 |

SQLite 事务完成预算预占、任务建立和幂等记录。状态不明的启动保持预占，确认未启动后才能退回；重启、换宿主、提高 revision、改变错误分类或执行 `repair/reset` 都不能清零总预算。Python 已要求升级时直接停止自动重试，不按控制器剩余额度继续。

故障 fingerprint 由规范化诊断、错误位置、工具链、目标与分类器版本形成，排除时间戳等噪声；另保留 source/input digest。精确故障键用于诊断去重，episode／run 总预算防止通过修改错误文本产生无限新预算。

## 6. 构建自修复的具体设计

### 6.1 诊断输入与分类

主输入使用当次 `gate_build.py` 捕获的 `evidence/phase4/build_stdout.log`、声明产物检查、静态检查 JSON、签名 manifest 以及当前 repair packet。`out/.../build.log` 仅作补充，并校验目标和时间，避免把旧构建日志当成本次证据。

已有 `ohos-dev-build-execution-diagnosis` 的日志与 fast-rebuild 脚本可以作为诊断模块复用。其基于日志文案的“成功”判断不参与业务放行；构建命令和验收结果仍来自环境 profile 与原 gate。

| 失败类别 | 首选诊断 | 修复路径 |
|---|---|---|
| 环境工具／路径／版本不匹配 | 核对已登记工具链、目标、环境摘要 | profile 允许的选择可调整；缺少工具或权限则明确阻塞 |
| 资源不足、网络抖动、构建进程中断 | 核实退出原因、磁盘／内存、进程树和旧作业状态 | 已确认停止且条件恢复后有界重试；不盲目全量清理或重复下载 |
| 编译语法、类型、头文件问题 | 提取首个有效错误和相邻诊断，关联声明文件与编译单元 | 生成范围内候选；通过 `repair` 回 P2 后导入，再走 P2→P3→P4 |
| 链接符号／已有目标依赖问题 | 查符号实现、GN target、依赖路径、编译单元 | 仅已有设计依赖的实现修复可走 P2；新外部依赖或目标变化回 P1 |
| 预期构建产物缺失 | 核对签名 `build_artifacts`、真实输出和目标 | 修复已有声明目标的实现；需要修改声明集合时回 P1，不能删掉缺失项换 PASS |
| metric／clang-tidy 阻塞 | 读取原始规则 ID、文件、位置和配置状态 | 范围内改码回 P2；不能关闭检查或放宽阈值 |
| 增量缓存／配置不一致 | 结合 GN 配置变更、工具链和缓存键排查 | 仅清理任务拥有且可重建的输出；配置变更后禁用不适用的 fast-rebuild |
| 契约、签名、证据 hash 异常 | 回读权威层，区分代码变化与证据损坏 | 停止自动补丁；使用原恢复流程，不能重写／重新签名旧证据掩盖问题 |
| 未分类失败 | 补充有限的只读诊断 | 可以形成候选诊断；依据仍不足时停止，不自动试错改码 |

首期快速编译仅作为诊断或候选验证。关闭 P4 必须再运行原 gate 的正式命令；不得通过替换目标、复用旧产物、跳过门禁或只跑一个编译单元完成阶段。

### 6.2 一次典型闭环

假设 P4 出现 `undefined reference`，诊断发现已批准组件中的实现遗漏：

1. 构建作业结束，保存不可变日志和退出记录；Python gate 发出有效 FAIL，父级确认当前阶段及输入基线。
2. 控制器建立 episode，选择构建诊断、C++ 和相关依赖模块；生成定位到文件／符号的任务上下文。
3. worker 在候选工作区生成补丁和修复说明。检查器验证文件范围、基线、补丁规模及禁止项；必要的独立 reviewer 验证“实现修复”判断。
4. 父级执行 `advance.py repair --reason ...`；Python 接受后 sync，原 P2 及后续证据失效，P1 契约和其有效确认保留。
5. 在源码写入锁内再次核对基线，将候选补丁导入；若用户或其他任务已改动同一基线，重新对账，不覆盖现有改动。
6. 按现有流程运行 P2、P3、P4。构建 PASS 后记录“构建恢复”；仍须完成受影响的测试与后续门禁，满足计划后才记录“修复已验证”。
7. 只有后续交付也合格，这个样本才计入完整交付收益；若 P5 暴露回归，将同一修复链标为回归／重新打开，不把之前 P4 PASS 当最终成功。

若第 3 步发现必须新增设计未覆盖的依赖，改为形成 P1 变更包，复用已有设计确认流程。无需为范围内的每次读日志、修改候选和重跑额外设置确认点。

## 7. 长作业、互斥、取消与崩溃恢复

### 7.1 受管作业执行

新增 `ExecutionSupervisor` 运行确定性命令。MCP 工具提交后立即返回 `operation_id/job_id`，日志通过游标读取；执行器持续写文件，避免将大型构建日志全部放入内存或塞回模型上下文。

现有远端 stdio 逐条等待请求处理，不能让一个构建请求长期占住它。拟将执行器放在独立受管进程中，多条 parent／worker 连接通过本机认证通道接入同一执行器；数据库保存作业状态，不用“断开 MCP 后仍留着一个子进程”冒充可恢复服务。

作业状态建议：`prepared → starting → running → collecting → validating → completed`；异常分支为 `failed / cancellation_requested / stopped / outcome_unknown`。`completed` 表示作业生命周期结束，业务是否 PASS 另存。

执行接口只接受登记的 gate／诊断操作及结构化参数，服务端构造 argv；不提供任意 shell 文本入口。运行 profile 绑定工具、源码、输出目录、目标与 timeout。原 gate 内部的构建由 supervisor 包围整个进程树管理，避免重复启动第二次正式构建。

### 7.2 资源互斥与旧进程问题

- 资源键包括规范化的 pipeline 路径、真实源码工作区、输出目录和设备 ID；按固定顺序取锁，解决路径别名、相同输出目录和死锁问题。
- 将所有源码／测试／GN 写入纳入 `workspace_write` 互斥。构建读取的源码也要稳定：首期同一工作区的写入和构建串行。
- 任务租约表示 agent 领取权；作业所有权表示进程与资源占用，两者分开。agent 失联时，只要作业仍活着或结果未知，资源继续保留。
- 租约过期进入 `needs_reconcile`，确认旧进程树已终止或其工作区已可靠隔离后才能重新派发。不得仅因为心跳超时就换 owner。
- 受管执行与 legacy Python CLI 使用同一资源锁协议；实现时明确顶层锁拥有者与内部 gate 的核验／重入方式，不允许 Node 先持锁、Python 再阻塞获取同一非重入锁。
- operation 身份从受信任执行通道授予并核验，不能仅靠 worker 可填写的环境变量或 `parent` 字样授予写入权限。

首期 supervisor 验收优先 Linux／WSL，取消覆盖进程组及其后代。Windows 后续用相应进程树管理机制独立验收；不能仅凭杀掉父 PID 就宣称所有构建进程已停止。

若真实宿主无法约束 worker 对主工作区的直接写入，先采用独立候选目录及受控补丁导入；不能验证该边界的环境只开放建议模式。对多仓 OHOS 工作区，快照记录各子仓 HEAD 与未提交内容 hash，不假设单个 Git worktree 自动覆盖整个源码树。

### 7.3 幂等与不确定结果

| 中断位置 | 恢复动作 |
|---|---|
| intent 已入库，进程尚未启动 | 在同一 operation 下核对启动记录，最多启动一次；确认未启动可退回预算预占 |
| 进程已启动但控制器未收到响应 | 按 job、进程身份和开始时间找回；不能只用 PID 判断，防止 PID 复用 |
| gate 已写 manifest，结果尚未入库 | 验证 operation、manifest entry、artifact hash、epoch 和输入快照，再补 receipt |
| Python 已 repair／advance，数据库仍是旧阶段 | 调用只读 inspect 并 sync，以 Python 为准；不重放可能有副作用的操作 |
| 补丁已导入但状态提交失败 | 比较导入前后 digest，确认已导入后续接；基线不一致则对账，不重复叠加补丁 |
| 取消请求已发出但进程状态未知 | 保持资源隔离与 `outcome_unknown`；确认整棵进程树停止后再重派 |
| P8 发布或远端 CI 状态未知 | 先查远端结果和已有证据，避免重复发布；首期不自动处理发布副作用 |

在签名记录中增加 `operation_id/input_digest` 时采用兼容版本扩展，由受信任执行边界传入。旧记录保留原始字节和校验方式，不能回填字段后重签。没有执行关联字段的旧运行先按互斥快照和证据区间保守对账；有歧义时进入 `needs_reconcile`。

长作业期间状态查询读取纯读投影。原 `advance.py status/next` 可能刷新维测／导航文件，不能在持有写入作业时被当作无副作用查询并发调用。新增只读 bridge 字段应复用已有解释函数，保持与真实门禁语义一致。

## 8. 跨任务自迭代闭环

### 8.1 迭代对象与自动化等级

自迭代首先改进策略、上下文和诊断顺序；不修改模型权重。控制器代码、Skill 脚本与新能力也能由系统提出改进，但进入独立版本变更流程。

| 等级 | 对象 | 允许的自动化 |
|---|---|---|
| E0 观测 | 有效运行数据、失败聚类、上下文使用 | 自动采集、聚合、给出候选，不影响运行 |
| E1 受限策略 | 已登记可选模块的排序、已批准只读诊断的顺序、已批准修复策略的选择 | 在预设发布范围内自动评测、影子、灰度和晋级；不得移除必需模块、增加权限或提高预算 |
| E2 内容与实现 | 新 Skill、Prompt 正文修改、诊断脚本、控制器算法 | 自动生成候选版本和测试／评测结果，经过正常代码评审后发布 |
| E3 业务约束 | gate、签名规则、consent、需求／AR 验收、测试断言与质量阈值 | 不进入自迭代自动改写；如业务需要调整，另走明确需求和设计流程 |

首期先启用 E0 和任务内自修复，完成评测闭环后在同一方案内开启 E1。E1 的可改字段、数值边界、灰度范围、评测预算和回滚条件形成一次批准的发布策略，范围内候选无需逐个重复确认。未配置该发布策略时停在候选状态，不自行推定授权。

### 8.2 从经验到版本

```text
已核验事件／修复结果
  → 按可比环境聚合失败及成本
  → 提出单变量候选
  → 静态约束检查
  → 历史回放 + 独立留出集
  → 沙箱执行评测
  → 影子运行（计算建议，不改变实际动作）
  → 限定新 run 的灰度
  → 达到准入标准后设为默认版本
  → 持续观测；回归时撤回版本
```

规则型候选可以由代码产生；需要语义归纳时，发布一个受预算约束的宿主分析任务。宿主离线或额度不足时保存候选，不能假设后台自动拥有模型推理能力。

### 8.3 有效样本和防止错误学习

一次经验至少关联：`run/episode/task/attempt/operation`、源码与输入 hash、契约与策略版本、环境与工具链、推荐模块、实际使用的可观测程度、候选补丁 hash、执行结果、核验结果、成本和后续回归。

- `execution_status`、`gate_verdict`、`workflow_status`、`repair_outcome` 分字段保存。P8 预检是待确认；未启动的命令是执行前阻塞；二者都不能归为业务 PASS／FAIL 的修复样本。
- 只将父级重新校验过的证据用于修复效果判断。模型自报、来源未知日志、本地旧 experience JSON 不能直接计入晋级样本。
- `selected_modules` 与 `observed_used_modules` 分开；宿主不可观测的使用信息标记未知，不按“被推荐”计算成功归因。
- 相同 run 的多次 retry 不当成多个独立成功案例。数据按需求／故障族分组拆分，避免同一失败的近重复样本同时进入训练集和留出集。
- 未完成后续验证的修复标为 `provisional`；发生 P5／P7 回归时关联原补丁并修正效果统计，保留原历史事件。
- 数据按项目、平台、工具链、构建目标、模型／宿主和缓存条件分层；未经跨域评测的规则不自动推广到其他工程。
- 日志只进入受控数据区，模型使用脱敏片段和证据引用。日志内出现的指令按数据处理，不能直接生成执行命令。

### 8.4 评测、灰度与回滚标准

| 环节 | 判定规则 |
|---|---|
| 静态检查 | 不能改锁定字段；必需能力覆盖、依赖闭包、路径范围和策略 schema 全部通过 |
| 历史回放 | 先判断候选路由和动作是否合法；回放不能证明新补丁可以构建成功 |
| 执行评测 | 同输入、代码、模型和环境运行 baseline／candidate，原 gate 标准完全相同；构建／测试以实际结果为准 |
| 数据充分性 | 默认至少 20 个独立、可比的历史 episode 进入候选筛选，留出集不少于 10 个独立 episode；不足时只做影子，不做自动晋级 |
| 收益与质量 | 合格完成率的配对非劣效评估通过，且至少一项成本／耗时指标有可重复改善；没有统计把握则继续收样或保留基线 |
| 灰度 | 默认只覆盖指定项目中按 run ID 稳定分配的 10% 新 run，并限制最大试点数量；不对同一源码目录同时执行两个写入方案 |
| 回滚 | 发现越权、假 PASS、证据错误立即冻结候选；质量／成本超出发布策略阈值则停止灰度并回到上一稳定版本 |

上述样本量和灰度比例是初始操作门槛，不表示达到数量即有统计显著性。具体非劣效容忍度、置信水平、成本阈值、最小可检出收益和最大试点数量需作为发布策略在实验前固定；未配置完整则不能自动晋级。

每个 run 在启动时固定策略版本。版本撤回后，新 run 使用稳定版；受影响的在途 run 在安全检查点暂停／对账后显式切换，保留已有预算与证据。回滚策略不自动回滚用户源码；由坏策略导入的补丁单独标记、复核并走修复路径，不能用版本切换伪装代码已经恢复。

## 9. 数据结构、接口与代码归属

### 9.1 数据结构

继续使用远端 SQLite，不新增并行的 JSON 运行数据库。下面是逻辑实体，落地时可以合并表，字段必须保留其职责：

| 实体 | 关键字段／约束 |
|---|---|
| `run_policy_bindings` | run、不可变 policy hash、模块版本、自动化范围、资源与预算 profile；切换保存历史 |
| `repair_episodes` | root run、触发证据、分类／fingerprint、状态、原因链、剩余／已用预算、修复结果 |
| `repair_work_items` | episode、父 task、唯一 work item ID、diagnose／patch／review／verify 类型、关联 attempt；不覆盖业务阶段 |
| `execution_jobs` | operation、task、命令 profile、input digest、进程身份、资源键、状态、日志游标、退出信息 |
| `operation_intents` | 操作类型、幂等键、参数 hash、预占、启动／结果状态；与原 `operations` 的完成结果兼容 |
| `resource_owners` | canonical resource、owner operation、epoch、进程状态、隔离状态；资源释放必须满足停止／完成条件 |
| `budget_ledger` | root run／episode、预算种类、reservation ID、reserved／consumed／released、关联 job；唯一键防重复计费 |
| `validated_receipts` | 证据 entry ID、artifact hash、输入基线、有效 epoch、验证者版本、原始 verdict 与用途 |
| `policy_candidates` | 来源 episode 集合、变更 diff、适用域、父版本、风险等级、候选 hash、状态 |
| `evaluations`、`policy_releases` | 数据集版本、独立分组、baseline/candidate、指标与原始记录、审批／发布策略、灰度范围、回滚点 |

现有 `events` 继续作为审计序列。观测和统计作为其投影，不反向修改原事件。用户改了原始需求而创建新 run 时，显式记录 lineage；不能通过自动换 run ID 绕开原有修复总预算。

控制器不在等待构建／模型任务期间持有 SQLite 写事务。采用短事务保存 intent 和状态，再异步执行；回收结果时重新检查 revision、owner、input digest 和 operation 身份。

### 9.2 拟议接口

保留远端现有 `ohos_task_*`、`ohos_requirement_*` 和 `ohos_delivery_*` 的名称与输入契约。已有 `ohos_task_context` 输出扩展模块、修复上下文和策略版本。新增接口如下，当前尚未实现：

| 接口 | 调用者 | 主要输入与返回 |
|---|---|---|
| `ohos_delivery_gate_start` | 持有效任务凭证的 worker；受管父级 | task／attempt 凭证、gate ID、结构化参数、expected revision、幂等键；返回 job／operation，gate 由阶段 allowlist 限定 |
| `ohos_operation_status` | 该任务 worker 或父级 | operation ID、日志游标；返回执行状态、有限摘要、artifact refs、证据核验状态 |
| `ohos_operation_cancel` | owner 范围内 worker 或父级 | operation ID、原因、幂等键；先返回取消请求，停止确认后状态另行更新 |
| `ohos_repair_plan` | 父级 | run、失败证据引用、expected revision；返回绑定基线和预算的计划，不执行补丁 |
| `ohos_repair_schedule` | 父级 | episode、plan digest、expected revision、幂等键；预占预算、建立子工作项，返回待派发角色 |
| `ohos_evolution_propose` | 有策略维护能力的父级 | 适用域、样本快照；生成候选和解释，不直接改活动策略 |
| `ohos_evolution_evaluate` | 策略维护角色 | candidate hash、固定数据集、评测预算；异步返回 evaluation job |
| `ohos_policy_release` | 发布服务或授权维护者 | candidate／evaluation digest、发布策略、灰度范围、expected version、幂等键；准入检查后发布 |
| `ohos_policy_rollback` | 发布服务或授权维护者 | release ID、稳定目标、原因、幂等键；停止新分配并列出受影响 run |

自修复 worker 沿用 claim／context／heartbeat／submit／release。新增工作项由 `work_kind` 分派校验器：业务任务走原 workflow；补丁任务提交 patch manifest；诊断任务提交证据引用。工作项 ID 不与现有 `run:phase:revision` 业务任务 ID 冲突，业务阶段仍由原权威层决定。

operation 查询也要验证资源访问范围，不能因为知道 ID 就读到其他 run 的日志。parent／worker 分面继续作为工具接口约束；自动改码与发布所需的真实文件／进程权限由部署 profile 实施并验收。

补丁导入由内部受控操作执行，至少检查：父基线匹配、允许路径、符号链接与路径穿越、未覆盖用户新改动、受保护脚本及证据未修改、必要检查已通过。**文件白名单不能证明行为不变**；公开 API、依赖和验收边界有疑义时必须交独立审查或回 P1。

```text

  workflows/
```

## 10. 分阶段实施与交付边界

| 阶段 | 主要变更 | 交付与退出条件 |
|---|---|---|
| M0 基线与契约 | 引入审阅过的 GitCode 主干，保存本地快照；记录 baseline；新增策略／作业／修复契约 | 远端原 56 项测试通过；本地有价值用例迁入；不把已复现的错误行为当正确兼容要求 |
| M1 执行可靠性 | supervisor、操作 intent、资源隔离、取消、纯读状态、执行关联与幂等、预算账本 | 双连接／崩溃／租约过期测试通过；旧作业未知时不能重派；已有 CLI 与受管入口互斥 |
| M2 模块融合 | 迁入 registry 与 failure 策略；上下文扩展和结构化失败 | SA／NAPI／C++、构建诊断样例可准确选模块；环、缺模块、缺能力、版本漂移均可诊断 |
| M3 构建自修复 | episode、候选补丁、检查／导入、Python repair/reset、重新验证 | 实际 OHOS 工程中完成一次环境重试与一次 P4→P2→P4 修复；预算与无进展停止可复现 |
| M4 经验与评测 | 有效事件投影、候选生成、数据分组、回放、执行评测、影子比较 | P8 预检／未执行失败不污染样本；可追溯一次候选从证据到评测的全过程 |
| M5 受控自迭代 | E1 发布策略、固定版本、灰度与回滚 | 在配置完整且数据充分的领域完成候选→评测→有限灰度→晋级／撤回；回滚不改写历史证据 |
| M6 后续扩展 | 需求结构返修、P5／P7 策略、更多环境和宿主；再评估 SDK 替换 | 每扩一种真实宿主／平台均有集成验收；范围扩展独立于策略自动晋级 |

M3 是首个可用交付点，提供“融合 + 构建自修复 + 经验采集”。M5 才构成完整的“自修复 + 自迭代”版本，不能在只有失败率聚合时宣布自迭代已完成。

实施顺序以 M1 的执行可靠性为先。M2 的纯路由工作可以独立准备，但在完成资源隔离前不启用无人看护的修复执行。

## 11. 验收清单与指标

| 编号 | 必须验证的场景 | 预期结果 |
|---|---|---|
| AC-01 | 本地和远端接口融合 | 同一个 run 只有远端正式状态机；R5／GA／consent 约束保留 |
| AC-02 | 模块环、缺依赖、缺必需能力、模块被原地修改 | 拒绝无效上下文或回退到已固定的有效策略，输出具体原因 |
| AC-03 | 一次实际构建故障自动修复 | 诊断→候选→P2 回退→原 gate 再验证闭环，证据能关联到同一次修复 |
| AC-04 | 需要新依赖／新增设计产物的修复 | 回 P1，不删验收项，不扩大自动补丁范围 |
| AC-05 | 进程启动后断线、租约过期、取消超时 | 查询可用；旧进程状态未知时锁不释放，无重复构建和并发导入 |
| AC-06 | 相同幂等请求重放、启动结果丢失 | 返回原 operation 或进入对账，不能产生第二次副作用 |
| AC-07 | 重启、换宿主、revision 更新和 repair/reset | episode／run 消耗保留，预算不能重置；停止原因可解释 |
| AC-08 | 用户在生成候选期间修改源文件 | 导入前发现基线漂移，保留用户修改并重新对账 |
| AC-09 | P8 预检正常退出、前置状态读取失败 | 分别记为等待确认、执行前阻塞，不当作修复成功或已执行 gate 失败 |
| AC-10 | 修复后 P4 通过而 P5 回归 | 修复仍未验证完成／重新打开；失败不能被历史构建成功掩盖 |
| AC-11 | 候选来自近重复样本／留出集泄漏／不可比环境 | 拒绝错误归因或自动晋级，保留 baseline |
| AC-12 | 候选试图改 gate／必需模块／预算上限／权限 | E1 准入直接拒绝；E2 变更进入正常代码评审 |
| AC-13 | 灰度发生质量回归 | 停止新分配并撤回版本，识别受影响 run；预算与证据历史不变 |
| AC-14 | 未配置真实宿主推理或发布策略、样本不足 | 明确等待宿主／停留候选，不声称后台推理或自动晋级已生效 |
| AC-15 | 原签名链／consent／功能指纹和 legacy CLI 回归 | 原有权威测试通过，锁和字段扩展不改变业务 PASS 标准 |

核心指标统一口径：

- **合格完成率**：满足同一最终验收标准的 run 占比；不能只比较 P4 通过率。
- **自动修复成功率**：进入自动修复的独立 episode 中，完成计划规定再验证的比例；另报全部失败的可自动处理覆盖率。
- **一次修复命中率**：首个实际补丁即完成再验证的 episode 占比；重试和补丁分开计。
- **成本与耗时**：每次合格交付的构建机器时间、模型实际用量或可观测代理指标，以及含等待／不含人工等待的耗时。
- **稳定性**：重复执行次数、过期 attempt 提交拒绝数、未知作业滞留时间、预算耗尽次数、回归与回滚次数。
- **人工介入**：计划内业务确认与非计划故障干预分开，避免将取消必要评审记为“提效”。

每一轮评测固定数据集和环境，采用同宿主／模型的配对比较：A 为远端基线，B 为融合路由，C 为路由与自修复，D 为稳定自迭代策略。使用相同最终门禁，报告失败案例和未测项；不预先承诺节省百分比。

## 12. 迁移、退出与首轮评审结论

迁移在实施阶段执行：先保存本地未提交的实现和当前验证快照，再引入远端主干，迁移独立策略组件和对应有效测试。旧 `dsh-workflow/.runtime` 的需求 completed 状态与经验成功记录不转成可信运行状态；如要接续，重新通过正式文档／Python 证据核验建立绑定。

现有远端数据库采用增量 migration；升级前做一致性备份并停止活动写入。新增字段给旧 run 使用固定 baseline 策略，先以 observe 模式接管。运行模式每个 run 固定为 legacy、observe 或 managed：observe 只建议；managed 独占受管执行；两种写入模式不同时操作同一 pipeline。

回退分两层：策略回退只改变后续分配；运行时回退需停作业、检查数据库 schema 兼容性，再切回旧程序或已备份状态。不能在存在活动 writer 时恢复旧数据库。迁移后新增的用户产物不因软件回退被直接覆盖。

**建议本轮通过的设计基线：**

1. 主干选 GitCode，保留一套正式任务和业务状态，吸收本地策略组件。
2. 先把 P4 自修复跑通；所有源码／测试修复以现有 Python repair/reset 和重新验证为准。
3. 先完成受管长作业、资源恢复和持久预算，再开放连续自动修复。
4. 自迭代从可核验数据起步；E1 限定为批准范围内的策略调整，E2 产出可评审版本变更。
5. M3 交付首个可用版本，M5 完成可评测、可灰度、可回滚的完整自迭代闭环。

本稿使用的轮次、样本量和灰度比例均为建议默认值。实际实施不需要为普通诊断和每次范围内重试反复请求确认；只有缺失事实、既有业务门禁、越出已批准范围或发布策略要求时才需要用户决定。
